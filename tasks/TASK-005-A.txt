## Required Changes

1. A1 — Make create and edit validation match the established backend loan-option contract:
   - required `min_amount` is finite and `>= 0`;
   - required `max_amount` is finite, `> 0`, and `>= min_amount`;
   - required `interest` is finite and `>= 0`;
   - required `months` is a positive safe integer;
   - optional `ingreso_minimo` is `null` when blank and otherwise finite and `>= 0`;
   - category remains one of the existing six canonical Spanish values.
2. A2 — Reject blank, malformed, exponent, hexadecimal, non-finite, multiple-decimal, trailing-character, and otherwise partially parsed numeric input. Keep invalid input visible and show concise Spanish guidance. Never silently convert invalid input to zero.
3. A3 — Produce normalized JSON numeric values only after successful validation. Preserve existing API paths, payload keys, create/edit semantics, category values, and valid boundary behavior: zero minimum, zero interest, zero income, equal min/max, and one month are valid.
4. A4 — Handle API failures consistently for fetch, create, edit, and delete. Prefer a non-empty safe JSON `{ "error": <string> }` message; otherwise use a concise operation-specific Spanish fallback. Do not show raw exceptions, response bodies, stack traces, SQL details, credentials, tokens, or transport internals to the user.
5. A5 — Prevent accidental duplicate create/edit/delete mutations while the relevant request is pending. Provide clear progress/disabled feedback and restore usability after success or failure. Preserve delete confirmation and avoid refreshing the list more than once per successful mutation.
6. A6 — Keep authentication/header behavior and SharedPreferences key usage compatible. Missing tokens must not be invented or logged. Do not change backend authorization behavior.
7. A7 — Add deterministic tests that exercise behavior, not only helper-to-helper equality. Tests must cover validation/payload boundaries, safe error selection/fallback, and at least one widget-level interaction proving invalid submit stays open with no mutation and valid submit produces one normalized result or request. Add a widget-level or equivalent boundary test proving duplicate mutation prevention.
8. A8 — Preserve the current page purpose, routes, theme, category order, add/edit/delete controls, responsive Flutter/web compatibility, and unrelated application behavior. Improve only what is needed for this workflow; do not redesign the page.

Database/testing scope: pure Flutter/Dart tests with fake/injected boundaries. No live HTTP server, database, actual SharedPreferences store, accounts, runtime launch, or external services.
