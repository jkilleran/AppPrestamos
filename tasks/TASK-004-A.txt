Title: Validate admin-managed loan-option parameters before persistence

## Objective

Add strict server-side validation and normalization to loan-option create/update operations so malformed or
unsafe financial parameters cannot reach the model. Preserve the existing admin authorization guards.

## Why This Task

The Flutter admin form already sends numbers, and the create/update controllers already reject non-admins.
However, the backend currently checks only whether four values are present and otherwise forwards the payload
directly to PostgreSQL. Server validation is required because UI validation can be bypassed.

## Required Changes

A1. Preserve authorization precedence: missing/non-admin `req.user` returns 403 `{error:"No autorizado"}` before
payload processing and with zero create/update/delete model calls. Do not alter authenticated GET behavior.

A2. For both create and update, accept finite JSON numbers or strict base-10 decimal strings for min_amount,
max_amount and interest. Reject booleans, null/undefined, arrays/objects, blank strings, NaN/infinities,
hexadecimal, exponent notation and trailing characters. Normalize accepted values to numbers before the model call.

A3. Enforce the existing option contract used by loan-request creation: min_amount >= 0; max_amount > 0;
max_amount >= min_amount; interest >= 0. `months` accepts a safe positive integer or a digits-only decimal string
representing one; normalize it to a number. Do not introduce new business caps or change rate interpretation.

A4. `categoria_minima` may be absent/null/blank and then normalizes to `Hierro`. Otherwise accept only the existing
case-insensitive ranks Hierro, Plata, Oro, Platino, Diamante and Esmeralda, and pass the canonical spelling.
`ingreso_minimo` may be absent/null and then passes null; otherwise it follows the strict numeric parser and must be >= 0.

A5. Any invalid payload returns status 400 with exactly `{error:"Datos inválidos"}` and zero persistence calls.
Valid create calls the model once and returns 201; valid update calls the model once and returns 200. Preserve the
existing model argument field names and response bodies. Delete behavior remains unchanged except for its preserved guard.
