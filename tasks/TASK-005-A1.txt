## Required Changes

1. A1.1 — Numeric fields must preserve malformed user input long enough for the strict validator to reject it. Do not use a formatter that converts a different string into a valid value by deleting unsupported characters.
2. A1.2 — Through actual widget interaction, the following complete inputs must remain invalid and produce zero mutations rather than being submitted as transformed numbers:
   - decimal field: `1e3`, `0x10`, `12abc`, `-3`;
   - months field: `1.5`, `1e3`, `-3`.
   The dialog must remain open with concise Spanish validation feedback. The test must assert the original text is preserved when the chosen platform/test input mechanism supports it; otherwise it must directly prove that no transformed payload/mutation occurs.
3. A1.3 — Preserve numeric keyboard hints and multiplatform usability. Valid digits/one-dot decimals must remain easy to enter. Do not add a new dependency or globally change input behavior.
4. A1.4 — Strengthen `safeApiErrorMessage` so database/runtime diagnostic forms and line-control content fall back safely. At minimum reject case-insensitively:
   - `SQLSTATE` and SQLSTATE-style codes;
   - `detail=`, `constraint=`, database query diagnostics, and stack/file-location forms;
   - carriage return, newline, and other ASCII line/control separators in the candidate message;
   - existing password/token/authorization/URL/transport patterns.
5. A1.5 — Preserve safe concise backend messages such as `Datos inválidos`, `No autorizado`, `Opción no encontrada`, and `Error interno`.
6. A1.6 — Add direct pure regression tests for newly blocked diagnostic/control cases and widget-level regression tests for the destructive-filter examples. Do not replace existing assertions with weaker ones.
7. A1.7 — Preserve the remaining TASK-005-A behavior: normalized valid payloads, blank income as null, duplicate guards, retry restoration, safe fallbacks, routes/headers/categories/theme, and exactly one refresh after successful mutation.
